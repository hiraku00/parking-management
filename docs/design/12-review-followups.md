## 12.1 状態表示の視覚設計（絵文字の廃止）

### 問題

入金マトリクス（`app/admin/page.tsx`）と凡例が、状態を絵文字（`✅ ◐ ⏳ ⚠️ ○ — 免`）で
表している。絵文字はOS・フォントで見た目が変わり、サイズ・色・余白を制御できないため、
デジタル庁／Appleのような端正なUIにならない。10-design-system.md §10.2 で状態色は
定義済みなのに、記号だけ絵文字のまま浮いている。

### 方針

状態は引き続き **アイコン＋文字＋色** の3点で示す（U1）が、アイコンを絵文字から
**デザイントークンに沿ったインラインSVGグリフ**に置き換える。グリフは
`components/ui/icons.tsx` に追加し、マトリクスのセルと凡例、契約者ポータルの
`status-pill` で**同じ部品を共有**する（表示の一貫性を1か所で保証。10 §10.7）。

### セルの意味・色・グリフ対応

`lib/services/queries.ts` の `MatrixCellStatus` はそのまま。表示だけ差し替える。

| 状態             | 文言     | 色トークン  | グリフ（SVG、16px相当）                |
| ---------------- | -------- | ----------- | -------------------------------------- |
| `paid`           | 支払済み | `--good`    | チェック（`CheckIcon`、既存）          |
| `partial`        | 一部入金 | `--warning` | 半円（左半分塗り。`HalfCircleIcon`）   |
| `pending`        | 確認中   | `--warning` | 時計（`ClockIcon`）                    |
| `overdue`        | 滞納     | `--danger`  | 三角に感嘆符（`AlertTriangleIcon`）    |
| `unpaid`         | 未払い   | `--muted`   | 輪郭のみの丸（`CircleIcon`、塗りなし） |
| `void`           | 免除     | `--muted`   | 斜線入りの丸（`SlashCircleIcon`）      |
| `not_applicable` | 対象外   | `--faint`   | 横棒（`DashIcon`、または空セル）       |

- セルは `36px` 角の正方形。中央に `20px` のグリフを、状態色を `currentColor` で流し込む。
  背景は付けない（マトリクスは密なので、点で読ませる）。`overdue` だけ淡い
  `--danger-soft` の下地を敷いて視線を集める。
- セルは `<button>`（44px相当のタップ領域を内側パディングで確保）、`aria-label` は
  「田中太郎 6月 滞納」のように状態文言を読む（グリフは `aria-hidden`）。
- **凡例**は絵文字の羅列をやめ、グリフ＋文言のチップを横に並べる。実データのセルと
  同じ部品なので、凡例とマトリクスの見た目が必ず一致する。

```
凡例:  [✓]済  [◗]一部  [🕐]確認中  [▲]滞納  [○]未払い  [⊘]免除  [–]対象外
        ↑ すべて同じSVGグリフ＋状態色。上の絵文字は「そこにグリフが入る」イメージ
```

### 波及

- 契約者ポータルの `status-pill`（`components/portal/status-badge.tsx`）も、絵文字
  （`✅ ⏳ ⚠️ ❌ ●`）を同じSVGグリフに置き換える。`lib/design/status.ts` の
  `icon: string`（絵文字）を、グリフ名 `glyph: 'check' | 'clock' | …` に変える。
- トースト（`components/ui/sonner.tsx`）の絵文字アイコンも同様に統一する。
- 実装は「グリフ追加 → `status.ts` の対応表を絵文字からグリフ名へ → 参照箇所を差し替え」
  の順。ロジックは変えない。

## 12.2 承認・却下・返金のフロー

### まず用語を分ける（却下と返金は別物）

レビューで「却下したらどうなる？返金は？この管理から外れる？」という混同があった。
両者はまったく別の操作なので、UI・文言・内部処理すべてで区別する。

| 操作     | いつ                                                | お金の状態                     | 内部処理                                                      |
| -------- | --------------------------------------------------- | ------------------------------ | ------------------------------------------------------------- |
| **却下** | 振込報告（pending）を、入金が確認できないとき       | **まだ受領していない**         | `rejectTransfer` → `rejected`、配分を解放、請求は未払いに戻る |
| **返金** | すでに受領済み（**succeeded**）を返す必要があるとき | **受領済み。実際に返金が要る** | **未実装**（本§で新規設計）                                   |

- 却下は「あなたの振込を確認できなかったので、もう一度お支払いください」。お金はシステムに
  入っていない（契約者が振り込んだと申告しただけの状態）。請求は `open` に戻り、契約者は
  ホームで「❌ 確認できませんでした（理由）」を見て再度支払える。**返金ではない。**
- 承認時に金額は変えられない。金額違いは「却下 → 現金などとして正しい額で記録し直す」
  （06 §6.5）。この運用は維持する。

### 返金が必要になる場面（v1で保留していたが、先払い導入で必要性が増した）

現状 04-data-model.md §4.5 で `paid --> open` は「v1では起きない。返金に対応するときに使う」
と保留されている。しかし **先払い（最大12か月）を導入した**ことで、以下が現実的になった。

- **解約時の前払い分の払い戻し**: 12か月前払い → 3か月で解約 → 残り9か月分を返金。
- 二重払い・過払い（同じ月を2回払ってしまった）。
- カード決済後のクレーム対応。

よって返金フローを設計する（実装は別フェーズでよいが、設計は今固める）。

### 返金の状態遷移

```
succeeded --> refunded        （全額返金。配分を解放し、請求は open に戻る）
paid（invoice） --> open       （04 §4.5 で保留していた辺を、返金時に使う）
```

- 入金状態に `refunded` を追加する（`PAYMENT_STATUSES` に追加、CHECK制約も更新）。
- **部分返金はv1.5では対象外**（前払い9か月の払い戻しは「9か月分の入金を1件返金」ではなく、
  対象の請求単位で扱えば全額返金の組み合わせで表現できる。複雑な按分は入れない）。
  将来必要なら `partially_refunded` を足す余地だけ残す。

### 新規関数 `refundPayment`（`lib/services/payments.ts`）

```
refundPayment(db, {
  paymentId, reason, refundMethod: 'card' | 'bank_transfer' | 'cash',
  owner: { email }, now,
}): { ok: true } | { ok:false; error: 'not_found' | 'not_refundable' | 'stripe_error' }
```

処理（`markSucceeded` と対になる冪等な関数）:

1. 対象入金が `succeeded` であることを確認（それ以外は `not_refundable`）。
2. **カード（`method='card'`）** なら Stripe で返金する:
   `stripe.refunds.create({ payment_intent: stripePaymentIntentId }, { idempotencyKey: 'refund:'+paymentId })`。
   失敗したら `stripe_error` を返し、DBは変更しない。
   現金・振込は物理的な返金（手渡し・振込）なので、システムは記録だけ行う（`refundMethod` と
   メモに残す）。
3. batch で:
   - `payments.status = 'refunded'`、`refundedAt/refundedBy/refundReason/stripeRefundId` を設定
     （状態ガード `status='succeeded'` 付き）。
   - この入金の `applied` 配分を `released` に戻す。
4. `recalculateInvoicesForPaymentStatement` で対象請求の `status` を再計算（`paid → open`）。
5. **領収書の扱い（インボイス対応）**: 発行済みの領収書は**消さない**（発行時点の事実として
   残す。物理削除しない原則）。代わりに、登録番号がある事業者は
   **適格返還請求書（返還インボイス）**を1枚発行する。§12.2「領収書スキーマの変更」参照。
6. 監査ログ `payment.refund`（理由・方法・額）。

### スキーマの追加・変更（04-data-model.md へ反映）

- `payments` に列を追加: `refunded_at`（ts）、`refunded_by`（text）、`refund_reason`（text）、
  `stripe_refund_id`（text）。`PAYMENT_STATUSES` に `'refunded'` を追加し、CHECK制約を更新
  （後方互換の追加なので D12 の「後方互換の変更だけ許す」に沿う）。
- `receipts` を「領収書と適格返還請求書の両方」を入れられるようにする:
  - `kind` 列を追加（`'receipt' | 'credit_note'`、既定 `'receipt'`）。
  - 一意制約 `receipts_payment_uq`（入金1件に領収書1枚）を **`(payment_id, kind)`** に変更し、
    同じ入金に「領収書1枚＋返還請求書1枚」を持てるようにする。
  - 連番 `receipt_no` は領収書と返還請求書で**別系列にする**か、同系列で通し番号にするかを
    決める（税務上はどちらも可。実装が単純な**同系列の通し番号**を推奨）。

### 管理画面のフロー（`/admin/payments/[id]`）

現状: pending の振込には［承認］［却下（理由）］、succeeded には［領収書］だけ。

追加: `succeeded` の入金に **［返金する］** を出す（`confirm-dialog`）。

```
入金の詳細（succeeded）
  金額 ¥36,000 / カード / 2026-10-01
  対象月: 2026年10月〜2027年9月分
  [ 領収書 ]  [ 返金する ]        ← 追加

［返金する］→ 確認ダイアログ
  この入金を返金しますか？
  ・返金方法:  ◉ カードに返金（Stripe）  ○ 銀行振込  ○ 現金で返金
      （カード決済は既定でStripe返金。振込/現金は「返金済み」として記録するだけ）
  ・理由:  [ 解約に伴う前払い分の返金                    ]
  対象の請求は「未払い」に戻り、契約者のホームに表示されます。
  [ キャンセル ]  [ 返金する ]
```

- 返金後、その入金は状態 `refunded` になり、詳細に「返金済み（日時・理由・方法）」と
  返還請求書へのリンクを表示。対象請求はマトリクスで再び `unpaid`／`overdue` になる。
- **「この管理から外れる」ことはない。** 入金レコードは `refunded` として残り、監査ログにも
  残る（物理削除しない原則）。台帳上は「受領 → 返金」の履歴が両方見える。

### 契約者側の表示

- 返金された入金は、履歴で「返金済み ¥◯◯◯（理由）」と表示する（`status-pill` に
  `refunded` トーンを追加）。対象月は未払いに戻るため、ホームの主状態に反映される。
- 解約（アーカイブ）と組み合わせる場合、アーカイブ済み契約者はポータルにログインできない
  ので、返金の連絡は管理者が口頭・書面で行う前提（システムは台帳と返還請求書を用意する）。

## 12.3 管理画面のログアウト（404の解消）

### 問題

`app/admin/layout.tsx` のログアウトが `/cdn-cgi/access/logout` 直リンク。これは
**Cloudflare Access のエンドポイント**で、本番（Accessの背後）では動くが、**ローカル開発では
Accessが無いため404**になる。さらにローカルはオーナー認証を `DEV_OWNER_EMAIL` で
バイパスしている（`lib/auth/owner.ts`）ので、そもそも「ログアウトする対象のセッション」が
無い。

### 方針: ログアウトを1本のアプリ内ルートに集約する

直リンクをやめ、`/admin/logout`（アプリ内）に集約して、環境ごとに振り分ける。

- **本番（`APP_ENV==='production'`）**: `/admin/logout` は `/cdn-cgi/access/logout` へ
  リダイレクトする。Access側の「ログアウト後の遷移先」も設定し、ログアウト後に
  トップ（`/`）か「ログアウトしました」ページに戻す（05 §5.2 のAccess設定に追記）。
- **ローカル／プレビュー**: `/admin/logout` は404にせず、
  「開発環境では管理者ログインは固定です（`DEV_OWNER_EMAIL`）。ログアウトはできません。」
  と案内する小さなページを出す。［ダッシュボードに戻る］だけ置く。

これで、どの環境でもログアウトリンクが404にならず、意味も明確になる。契約者側の
`logoutAction`（Cookieを消す）は現状のままで問題なし。

### 実装メモ

- `app/admin/layout.tsx` のリンク先を `/cdn-cgi/access/logout` → `/admin/logout` に変更。
- `app/admin/logout/page.tsx` を追加（サーバーコンポーネントで `appEnv().APP_ENV` を見て
  本番は `redirect('/cdn-cgi/access/logout')`、それ以外は案内を表示）。
- 05-auth-security.md §5.2 の「ログアウトは `/cdn-cgi/access/logout` へのリンクにする」を
  「`/admin/logout` 経由にする（本番はAccessへ、開発は案内）」に更新。

## 12.4 支払い範囲選択のUI再設計と文言

対象: `app/portal/pay/page.tsx`、`app/portal/pay/prepay-selector.tsx`（[11](11-ui-redesign.md) §11.4）。

### 問題

1. 「お支払いの範囲を選んでください」の見出しと2枚の選択カードが**バラバラに置かれ**、
   まとまりに見えない。1つの選択ブロックとして囲みたい。
2. 「先払い」を選んだときの月数セレクト（「何か月分、先に払いますか？」）が、選択ブロックの
   **外**に離れて出るので、どの選択に属する設定なのか分かりにくい。選んだ選択肢の
   **一段下（子）**として現れるべき。
3. 文言 **「未払い分だけ払う」／「未払い分＋先払い」** の粒度が揃っていない
   （前者は動詞句「〜払う」、後者は名詞句「〜先払い」で平仄が崩れている）。

### 再設計: 1つの選択ブロック＋階層化

選択肢を1枚の枠（`.range-picker`）にまとめ、その中に2つの選択肢を縦に並べる。
「先払い」を選んだときだけ、その選択肢の**内側（インデントした子領域）**に月数セレクトを
差し込む。金額の内訳ブロック（未払い分／先払い分／合計）は従来どおり別ブロックで下に置く
（[前回の指摘](11-ui-redesign.md)どおり、選択カードと内訳は見た目を分ける）。

```
お支払いの範囲                                    ← ブロックの見出し（枠の中）
┌────────────────────────────────────────┐
│ ◉ 未払い分            2026年7月〜9月分    ¥9,000 │
│                                                │
│ ○ 未払い分 ＋ 先払い   来月以降もまとめて         │
│     ┊ ← 選択時だけ、子としてインデント表示        │
│     ┊ 何か月分、先に払いますか？                 │
│     ┊ [ 1か月分（2026年10月分）        ▾ ]      │
└────────────────────────────────────────┘

お支払いいただく金額                              ← 別ブロック（1枚の白）
  未払い分   2026年7月〜9月分            ¥9,000
  先払い分   2026年10月分                ¥3,000
  ─────────────────────────────
  合計                                 ¥12,000

[            次へ            ]
```

- `.range-picker`: 1枚の枠（`--surface`／角丸／`--line` 境界）。中の各選択肢は行で、
  選択中の行は `--blue-soft` の下地。行の境界は内側の区切り線。**選択肢は枠内の行**なので、
  「複数の独立カードが並ぶ」前回の形とも、内訳ブロックとも見た目が明確に違う。
- 月数セレクトは選択された「＋先払い」行の**中**に、左インデント＋細い縦線（`┊`）で
  親子関係を示して置く。未選択の間は出さない（段階的開示）。
- 内訳・合計ブロックは §11 で決めた「1枚の白いブロック＋区切り線」を踏襲。

### 文言の平仄を揃える

2つの選択肢を**同じ構造の名詞句（範囲ラベル）**に統一する。推奨は次のどちらか。

| 案        | 選択肢1          | 選択肢2                | 補足                                                             |
| --------- | ---------------- | ---------------------- | ---------------------------------------------------------------- |
| A（推奨） | **未払い分**     | **未払い分 ＋ 先払い** | どちらも「未払い分」を主語に、後者が加算を明示。最も誤解が少ない |
| B         | **未払い分のみ** | **未払い分と先払い**   | 「のみ」と「と」で対にする                                       |

- 推奨は **案A**。選択肢1をあえて「未払い分」だけにし、選択肢2で「＋ 先払い」を足す形にすると、
  「両方に未払い分が含まれる」ことが記号レベルで伝わる。動詞（払う）は各行に付けず、
  ブロック見出し「お支払いの範囲」と［次へ］に委ねる。
- 補足行（サブ）も平仄を揃える: 選択肢1=「2026年7月〜9月分」（対象の具体）、
  選択肢2=「来月以降もまとめて」（性質）。役割が違うので粒度差は許容だが、どちらも
  短い体言止めにする。
- 月数セレクトの見出しは「何か月分、先に払いますか？」を維持（ここは疑問形で自然）。

### 送信の仕組みは変えない

これは見た目と文言の変更で、`method="get"` で `count` を次のステップへ渡す仕組み
（11 §11.4、ブラウザの戻るで選択が消えない）はそのまま。`prepay-selector.tsx` の
state（`mode`／`months`）とレイアウトだけ組み替える。
