# 9. UX改善計画（契約者のスマホ体験を中心に）

作成日: 2026-09-13 / ステータス: **実装前の設計（レビュー待ち）**

Phase 0〜6 で実装した画面を、実機（本番URL・375px幅）とコードの両方で見直し、「若い人から高齢の方まで、スマホだけで迷わず払える」ことを基準に改善点を整理しました。実装は含みません。各項目は、そのままPRに切り出せる粒度まで具体化しています。

## 9.1 前提

- 契約者は**月に1回しか使わない**。毎回「初めて使う人」に近い状態で開く、と考えて設計する（操作を覚えてもらう前提にしない）。
- 主な利用環境はスマホ（iPhone Safari / Android Chrome）。QRからログインし、Cookieは180日有効（`lib/auth/contractor-session.ts`）。
- [07-screens.md](07-screens.md) §7.1 のUX方針（本文18px、主ボタン56px全幅、ステップ形式、アイコン＋文字＋色、専門用語を使わない）は正しい。**問題は、方針に実装が届いていない箇所と、方針では想定していなかった状況**にある。
- 優先度: **P0** = 誤解や操作の行き詰まりに直結する / **P1** = 分かりやすさが大きく上がる / **P2** = あると良い・運用の改善

## 9.3 改善の方針

1. **ホームは「今の状態」を1つだけ大きく伝え、主なボタンは1つだけにする。** 一覧や内訳は必要な人だけが開く。
2. **「払う必要がある分」と「先に払ってもよい分」を分ける。** 必要な額を大きく、前払いは控えめな選択肢にする（U1）。
3. **操作の結果は、必ずその場で分かるようにする。** 完了画面を用意し、次に何が起きるか（「確認できたら ✅ が付きます」）まで書く（U2, U5）。
4. **行き止まりを作らない。** 途中でやめた・戻った・却下された、のどの状態からも、ホームのボタン1つで続きができる（U3, U11）。
5. **ブラウザの［戻る］で壊れない。** ステップはURLで表し、状態をクライアントに持たない（U6, U7）。

### 言葉の置き換え

| 現状                       | 変更後                                          | 理由                                           |
| -------------------------- | ----------------------------------------------- | ---------------------------------------------- |
| 1か月分（2026年9月〜9月）  | **9月分**                                       | 範囲の表記は1か月分では不要                    |
| 2か月分（2026年9月〜10月） | **9月分と10月分**                               | 「〜」の範囲表記より、並べた方が読み違えにくい |
| 前払い（10月分）           | **10月分も一緒に払う**                          | 「前払い」という言葉を使わずに済む             |
| クレジットカード等         | **カード・スマホ決済**（Apple Pay・Google Pay） | 使える手段が名前から分かる                     |
| 振込を報告する             | **振り込みました**                              | 押す人の行動そのものをボタンにする             |
| この内容で進む             | **次へ** / **お支払いへ**                       | 何が起きるかを明確にする                       |
| この領収書を印刷する       | **保存・印刷する**                              | スマホでは印刷よりPDF保存が主な用途            |
| ポータルに戻る             | **ホームに戻る**                                | 「ポータル」は利用者にとって意味のない言葉     |

## 9.4 画面設計（契約者）

### 9.4.1 ホーム（`/portal`）: 状態を1つに絞る

ホームに出す「主な状態」を、次の優先順位で1つだけ決めます。判定は純関数にして単体テストします。

```ts
// lib/domain/portal-home.ts（新規・純関数）
export type HomeInvoice = {
  id: string
  month: YearMonth
  remaining: number
  timing: 'overdue' | 'current' | 'future' // 今月より前 / 今月 / 前払い対象
  pending: boolean // 確認中の配分が付いている
}

export type HomeState =
  | { kind: 'card_in_progress'; paymentId: string; months: YearMonth[]; amount: number } // U3
  | { kind: 'rejected'; paymentId: string; months: YearMonth[]; reason: string | null } // U11
  | { kind: 'needs_payment'; overdue: boolean; months: YearMonth[]; amount: number } // U1
  | { kind: 'waiting_confirmation'; months: YearMonth[] } // 振込の確認待ちだけが残っている
  | {
      kind: 'all_paid'
      paidThrough: YearMonth | null
      nextMonth: { month: YearMonth; amount: number } | null
    }

export function deriveHomeState(input: {
  invoices: HomeInvoice[]
  pendingCardPayment: { paymentId: string; months: YearMonth[]; amount: number } | null
  latestRejected: { paymentId: string; months: YearMonth[]; reason: string | null } | null
}): HomeState
```

判定のルール（上から順に評価）:

1. 自分のカード決済が `pending`（Checkout の手続き中）→ `card_in_progress`
2. 最新の却下された振込があり、その対象月がまだ未払いで確認中でもない → `rejected`（古い却下は出さない）
3. `timing` が `overdue` または `current` で、`pending` でない請求がある → `needs_payment`（金額はその合計。**`future` は含めない**）
4. 未払いは `pending` のものだけ → `waiting_confirmation`
5. それ以外 → `all_paid`（`future` の請求があれば `nextMonth` に入れる）

`needs_payment` のとき（滞納あり）:

```
┌─────────────────────────────┐
│ 田中太郎 様            区画 A-3 │
├─────────────────────────────┤
│ ⚠️ お支払いが遅れています        │ ← 赤。文字あり（U9）
│                             │
│ 8月分と9月分                   │
│ ¥6,000                       │ ← 32px
│                             │
│ [       お支払いへ進む       ] │ ← 56px・全幅。主ボタンはこれだけ
│                             │
│ 内訳を見る ▾                   │ ← 2か月以上のときだけ。開くと月ごとの金額
├─────────────────────────────┤
│ ⏳ 7月分の振込を確認しています    │ ← 確認中があれば、補足として1行
├─────────────────────────────┤
│ お支払いの履歴 ›                │
└─────────────────────────────┘
```

各状態の表示内容:

| 状態                        | 見出し                               | 主ボタン                 | 補足                                                                           |
| --------------------------- | ------------------------------------ | ------------------------ | ------------------------------------------------------------------------------ |
| `card_in_progress`          | 💳 カードのお支払いが途中です        | ［お支払いを続ける］     | ［やめる］（副ボタン）。「30分たつと自動で取り消されます」                     |
| `rejected`                  | ❌ 9月分の振込が確認できませんでした | ［もう一度お支払いする］ | 理由を表示。「ご不明な点は 03-xxxx-xxxx までご連絡ください」（設定の電話番号） |
| `needs_payment`（今月のみ） | 9月分 ¥3,000                         | ［お支払いへ進む］       | 支払期日があれば「9月30日までにお支払いください」（U15）                       |
| `waiting_confirmation`      | ⏳ 9月分の振込を確認しています       | なし                     | 「確認できたら、ここに ✅ が付きます（通常1〜3日）」                           |
| `all_paid`                  | ✅ 9月分までお支払い済みです         | なし                     | `nextMonth` があれば、副ボタン［10月分を先に払う］                             |

その他:

- **履歴**はホームには直近3件だけを出し、［すべての履歴を見る］で `/portal/history`（新規）へ。各行は「9月分 ¥3,000 ✅ お支払い済み ［領収書］」。
- **ヘッダー**は氏名と区画を大きく1回だけ出す（「ようこそ、〜さん」の小さい文字は削除）。［ログアウト］は画面の最下部へ移す（押し間違えると、QRカードを探し直すことになるため）。
- `?transfer_reported=1` は使わない（U2 は完了画面で解決する）。

### 9.4.2 お支払い: ステップ 1/2（`/portal/pay`）

- **ドロップダウンをやめ、選択肢をすべて見せる大きなカード型のラジオボタンにする**（U6）。
- **フォームは `method="get"` で `/portal/pay/method` へ送る。** Server Action もクライアントの状態も使わないため、［戻る］で選択が消えない（U7）。
- 選択肢は「古い月から、その月までをまとめて払う」形（旧UIと同じ考え方）。**初期選択は「払う必要がある分」**（`overdue` と `current` の合計）。`future` の月は「〜も一緒に払う」と表記する。
- **選択肢が1つしかないときは、このステップを飛ばして** `/portal/pay/method?count=1` へ移動する。

```
┌─────────────────────────────┐
│ ‹ 戻る              ステップ 1/2 │
│ どの月の分をお支払いしますか？    │
│                             │
│ ◉ 9月分                ¥3,000 │ ← 1枚 64px以上。全体がタップ対象
│   お支払いが必要な分            │
│ ○ 9月分と10月分         ¥6,000 │
│   10月分も一緒に払う            │
│                             │
│ [           次へ           ] │
└─────────────────────────────┘
```

### 9.4.3 お支払い: ステップ 2/2（`/portal/pay/method?count=N`）

- 画面上部に「9月分 ¥3,000」を大きく再掲する（何を払おうとしているかを見失わないため）。
- 支払い方法は大きなカード2枚。**前回使った方法を初期選択にする**（直近の `succeeded` の入金の `method` から求める。DBから取れるので端末に保存しない）。
- 設定で無効にしている方法は出さない。有効な方法が1つだけならカードは1枚だけ出し、選択済みにする。
- ［お支払いへ］は既存の `startPaymentAction` に `count` と `method` を送る。［‹ 戻る］は `/portal/pay?count=N`（選択を保ったまま戻る）。
- `count` が不正・支払える件数を超える場合は `/portal/pay` へ戻す（URLを直接いじられた場合）。

```
┌─────────────────────────────┐
│ ‹ 戻る              ステップ 2/2 │
│ 9月分  ¥3,000                 │
│ お支払い方法を選んでください     │
│                             │
│ ┌ 💳 カード・スマホ決済 ─────┐ │
│ │  Apple Pay・Google Pay も可  │ │
│ │  すぐに完了します            │ │
│ └───────────────────────┘ │
│ ┌ 🏦 銀行振込 ──────────────┐ │
│ │  確認まで1〜3日かかります     │ │
│ └───────────────────────┘ │
│                             │
│ [        お支払いへ         ] │
└─────────────────────────────┘
```

カードを選んで押したあとは、Stripeへ移るまでの間「決済画面へ移動しています…」を全画面で表示する（二度押しと、何も起きていないという不安を防ぐ）。

### 9.4.4 銀行振込（`/portal/pay/transfer?count=N`）

1ページのまま、①②の番号で2つの区切りを付けます（銀行アプリへ行って戻ってきたときに、同じ画面で続けられるようにするため）。

```
   金額        ¥3,000        [コピー]
   銀行        みずほ銀行 丸の内支店
   口座        普通 1234567   [コピー]
   名義        チュウシャジョウ カンリタロウ [コピー]

② お振り込みが終わったら
   振込名義    [ タナカ タロウ          ]
               通帳や明細に出る名前（カタカナ）
   振込日      [ 2026/09/13 ]

```

- **［コピー］**（U12）: `components/portal/copy-button.tsx`（新規・クライアント）。`navigator.clipboard.writeText` を使い、押すと2秒間「コピーしました ✓」に変わる。クリップボードが使えない環境では、値を選択状態にする。
- **振込名義**（U4）: 初期値はフリガナ。**フリガナが無い場合は空欄のまま、入力例と説明を必ず表示する**（「例: タナカ タロウ」「通帳や明細に出る名前（カタカナ）」）。あわせて、管理画面の契約者フォームで、フリガナが空のときに「振込の照合に使います。入力をおすすめします」と表示する（必須にはしない）。

```
   9月分  ¥3,000
   お振り込みを確認できたら、ホームに ✅ が付きます（通常1〜3日）。
   [ ホームに戻る ]
```

完了画面は本人の入金であることを確認する（`payment.contractorId === 現在の契約者`。他人のIDなら404）。

### 9.4.6 カード決済の途中からの再開・取り消し（U3）

サービス層に2つ追加し、ホームの `card_in_progress` から呼びます。**スキーマの変更は不要**です（Checkout Session のURLは `sessions.retrieve(id).url` で取り直せる）。

```ts
// lib/services/payments.ts（追加）
export async function getPendingCardPayment(
  db: Db,
  contractorId: string,
): Promise<{ paymentId: string; months: YearMonth[]; amount: number; sessionId: string } | null>

export type ResumeCardCheckoutResult =
  | { kind: 'redirect'; url: string } // Session がまだ open → そのままStripeへ
  | { kind: 'completed'; paymentId: string } // 実は支払い済み → fulfillCheckout して完了画面へ
  | { kind: 'expired' } // 期限切れ → releaseAllocations 済み。ホームでは再び払える状態になる

export async function resumeCardCheckout(
  db: Db,
  params: { paymentId: string; contractorId: string; now: Date; stripeClient?: Pick<Stripe, 'checkout'> },
): Promise<ResumeCardCheckoutResult>

// 完了画面の `canceled=1` の処理（sessions.expire → releaseAllocations）もこれに寄せる
export async function cancelCardCheckout(
  db: Db,
  params: { paymentId: string; contractorId: string; now: Date; stripeClient?: Pick<Stripe, 'checkout'> },
): Promise<{ ok: true } | { ok: false; error: 'not_found' | 'not_pending' }>
```

- どちらも本人の入金で、`method='card'` かつ `status='pending'` であることを確認する。
- Server Action `resumeCardCheckoutAction` / `cancelCardCheckoutAction` を `app/portal/actions.ts`（新規）に置く。
- 統合テスト: 再開（open / complete / expired の3通り）、取り消し後に同じ月をもう一度払えること、他人の入金を指定すると拒否されること。

### 9.4.9 ホーム画面への追加（U16, P2）

- `public/manifest.webmanifest`、`public/icons/`（192px・512px、`apple-touch-icon`）を追加し、`app/layout.tsx` の `metadata` から参照する。`start_url` は `/portal`。
- **`display` は `standalone` にしない（`browser` にする）。** iPhoneでは、ホーム画面から単独のアプリとして開くと、Safariとは別の保存領域になり、QRでログインしたときのCookieが引き継がれない。その結果、ホーム画面から開くたびに予備ログインを求められてしまう。`browser` なら、アイコンから開いてもSafariで開くため、ログインが保たれる。
- ホームに1回だけ「ホーム画面に追加すると、次からすぐに開けます［やり方を見る］［閉じる］」を出す（閉じたことは `localStorage` に保存。端末ごとの設定で十分なため）。

### 9.4.10 予備ログインでフリガナも使えるようにする（U17, P2）

- `contractors.login_kana_key`（TEXT, NULL可）を追加する。値は `normalizeKana(nameKana)`（NFKC → ひらがなをカタカナに → 空白と「・」を除去）。migrationは列の追加だけなので、§8.3 のルール内で自動適用できる。
- 照合は「`login_key` で探す → 無ければ `login_kana_key` で探す」。フリガナで**複数人が一致した場合は失敗扱い**にし、失敗回数は数えない（同じ読みの人を取り違えないため）。管理画面では、同じフリガナの契約者がいれば登録時に警告する。
- 失敗時の文言（R6: 存在を推測させない）は変えない。

### 9.4.11 支払期日（U15, P2）

- `settings.payment_due_day`（INTEGER, NULL可, 1〜28。NULLは月末）を追加する。
- ホームに「9月30日までにお支払いください」を出す。滞納の判定（`timing='overdue'`、ダッシュボードの「滞納している人数」）は、期日を過ぎたかどうかで行うように変える。
